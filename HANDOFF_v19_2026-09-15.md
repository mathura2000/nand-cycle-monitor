## 2. Infrastructure note — Supabase auto-pause (UPDATED — v18's "stay reactive" decision reversed)

**v18 §2 recorded**: "User's explicit decision: stay on free tier, fix
reactively each time, rather than a keep-alive cron or paid upgrade. Don't
re-raise this unless the user does."

**This session, the owner raised it themselves** (from the
`athena-love-splash` session, prompted by a fresh round of Supabase
pause emails covering multiple projects in the org, not just this one)
and asked for a keep-alive cron. Built and live-verified:

- This project's Supabase database (`snmcikbbkbhzcbyrpqtt`) got a
  `_keepalive` table (RLS enabled, no direct table policies) plus a single
  `bump_keepalive()` RPC, grantable to `anon`, that only updates that one
  row's timestamp — deliberately narrower than a normal RLS policy grant,
  so the anon-reachable surface is exactly one function and nothing else.
- A local Node script in `athena-love-splash`
  (`scripts/supabase-keepalive/keepalive.mjs`) calls that RPC for this
  project and for `boating-dashboard` (the org's other active project),
  once a day, via a macOS **launchd** agent
  (`~/Library/LaunchAgents/com.athena.supabase-keepalive.plist`) rather
  than plain cron — catches up on wake if the Mac was ever asleep at the
  scheduled time, though the owner's Mac stays on continuously so this
  matters less than it would on a laptop.
- `busy-status-app` (the org's third project) was **left paused on
  purpose** — already dormant, and not referenced by any live code found
  in this session's cross-project audit, so it wasn't revived.
- **This lives in `athena-love-splash`, not this repo** — there's nothing
  to install or maintain here. If the cron ever needs changing, that's the
  repo to look in.

**Fallback plan if this ever isn't enough** (e.g. the Mac is off for a
stretch longer than the 7-day window): move to a `pg_cron` job running
inside Supabase itself, which wouldn't depend on any local machine being
on. Not needed yet — noted here so a future session doesn't have to
re-derive it.

**Don't re-raise the "keep-alive vs. stay reactive" question again** —
same instruction v18 gave, just pointing the other way now: this is
settled as "keep-alive, via the cron described above" unless the owner
says otherwise.
