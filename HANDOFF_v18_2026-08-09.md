## 2. Infrastructure note — Supabase auto-pause (NEW, will recur)

The Supabase free-tier project (`snmcikbbkbhzcbyrpqtt`) auto-pauses after
~7 days with no API traffic. Symptom: app shows "No data ingested yet" even
though the DB has real data — `/api/sheets?action=data` silently returns
empty arrays because the app swallows the Supabase connection error with
`?? []`. **Diagnosis:** check project status via Supabase MCP
(`get_project` / `list_projects`) *before* suspecting `.env.local`, ingest
gaps, or frontend bugs — it's the more likely cause and takes under a
minute to rule in/out. **Fix:** `restore_project`, then poll until
`ACTIVE_HEALTHY` (took ~2–3 min this time). No code or app restart needed.

User's explicit decision: stay on free tier, fix reactively each time,
rather than a keep-alive cron or paid upgrade. Don't re-raise this unless
the user does.

## 4. Transcript sourcing — updated map (supersedes the reference memory doc)

**Paywalled everywhere, confirmed this session:** Yahoo Finance
(`finance.yahoo.com/quote/.../earnings_call-...`) — renders only an
AI-generated summary paragraph + the first ~1 minute of real dialogue, then
a Quartr Silver/Gold upsell wall. This is true even loaded in a real
browser (not just server-side fetch) — it's a genuine paywall, not a
JS-rendering issue.

**New reliable source: stockanalysis.com** — full transcripts, no paywall,
no bot-block encountered. URL pattern:
`stockanalysis.com/stocks/{ticker}/transcripts/{story-id}-q{N}-{year}/`.
The `{story-id}` is the *same numeric ID* Yahoo uses in its own URL — if you
have a Yahoo transcript URL, you can usually swap the domain and ticker
casing and land on the working stockanalysis.com page directly. To find a
transcript for a specific real quarter (not knowing the ID), fetch
`stockanalysis.com/stocks/{ticker}/transcripts/` — it lists all entries with
working relative URLs and dates.

**Critical gotcha, costly to re-discover:** Yahoo/Fool/stockanalysis all
label transcripts using each company's own fiscal-quarter convention, not
the app's calendar-quarter buckets. For companies with a non-calendar fiscal
year (MU, MSFT, SNDK), "Q2 2026" in the URL is *not* the app's "Q2 2026"
row. Concretely, as of this session:

| Ticker | Fiscal offset | App "Q2 2026" = | App "Q3 2026" = |
|---|---|---|---|
| MU | ~2mo lag | fiscal Q3 FY26 (Mar–May, rpt Jun 24) | fiscal Q4 FY26 (Jun–Aug, rpt ~late Sep) |
| MSFT | FY starts Jul | fiscal Q4 FY26 (Apr–Jun, rpt Jul 29) | fiscal Q1 FY27 (Jul–Sep, rpt ~late Oct) |
| SNDK | FY starts ~late Jun | fiscal Q4 FY26 (Apr–Jun, rpt Aug 5) | fiscal Q1 FY27 (Jul–Sep, rpt ~early Nov) |
| AMZN/GOOG/META | calendar FY | calendar Q2 2026 (rpt late Jul) | calendar Q3 2026 (rpt late Oct) |
| SSNLF/HXSCL | calendar FY | calendar Q2 2026 (rpt late Jul) | calendar Q3 2026 (rpt late Oct) |

**Before pulling a transcript for MU, MSFT, or SNDK, always check what
fiscal quarter the app's target calendar bucket actually maps to** —
don't trust the label the source site gives it.

**EDGAR filing speed, recalibrated:** all four hyperscalers' Q2 2026 capex
figures were available via `/api/ingest/edgar-hyperscalers` same-day or
next-day after their earnings call (AMZN: called + filed Jul 31; GOOG:
called Jul 22, filed Jul 23; MSFT: called + filed Jul 29). Faster than the
"~5 weeks post-earnings" assumption in earlier planning — don't wait weeks
to run the EDGAR auto-refresh after a hyperscaler earnings call, try it
the same day.

## 6. New methodology: the 2-quarters-out forecast method

Full text lives in the `methodology` table (`field = 'forecast_2q_out'`),
but the short version, because this will come up again in ~90 days when Q3
2026 becomes the anchor and Q1 2027 needs populating:

**Never** flat carry-forward, **never** pure linear/trend extrapolation off
the two nearer points. Both were tried in spirit or considered and
rejected — flat carry-forward violates the standing no-fabrication
principle; pure trend extrapolation can directly contradict real guidance
you already have (this session: MU's Q2→Q3 capex_pct dropped
166.4→76.7, and a naive linear projection put Q4 at **-13%**, flatly
contradicting MU's own "above fiscal Q4 levels" quote).

**Instead:** build a judgment-based point estimate from whatever real
qualitative signal exists — full-year guidance, named capacity-expansion
projects with real dates, explicit H2/second-half commentary, comparative
guidance ("above X"). Nudge the 1-quarter-out forecast in the direction a
real quote supports; hold flat where no quote gives a directional signal.
Confidence should run meaningfully lower than the 1-quarter-out forecast.
`forecast_basis` must always name the specific quote used — never just say
"extrapolated."

## 7. Tooltip narrative rewrite — process worth repeating

Six rounds of editing turned an initial draft into the final six tooltips.
The pattern that emerged, useful for next time:

1. **Every bullet must carry information no other bullet in the same
   tooltip already carries.** Caught twice this session — a "real guidance"
   bullet that turned out to just restate two other bullets once you
   stripped out the padding (the actual net-new content was one fact:
   Microsoft's guidance was the single largest capex jump in the dataset),
   and a "these are estimates" caveat bullet that just repeated what
   "right where visibility is lowest" already said one bullet earlier.
2. **Name the actual vendor(s), not a generic group.** "Vendors gave real
   numbers" turned out to mean 4 of 8, split across two different kinds of
   evidence (capex guidance vs. shipment guidance) and split across supply
   vs. demand side — collapsing that into "vendors" hid the more
   interesting, more precise story.
3. **Lead with the so-what, not the evidence.** "All four vendors hit
   production milestones — SK Hynix did X, Samsung did Y, SanDisk did Z" got
   cut down to "supply is maxed out, not slacking" — the underlying facts
   moved to the "why," the takeaway moved to the front.
4. **A hedge/caveat bullet is a wasted slot if it doesn't tell the reader
   what to actually watch for.** The Q4 2026 "these are estimates" bullet
   got replaced with a pointer to the actual leading indicators worth
   checking (a hyperscaler easing off capacity language, a construction
   date pulled forward) — same low-confidence signal, but now actionable.
5. **Always sanity-check compound math before writing it into copy.** The
   session's own gap-level numbers (216.6, 254.4, 294.0, 342.5) were wrong
   by a constant +100 — a units mismatch (raw 100-based demand index minus
   already-zero-based supply index) that only surfaced while re-deriving
   numbers for an unrelated Gap Bar fix. The **deltas** (+37.8, +39.6,
   +48.5) were accidentally correct since the offset cancels in
   subtraction, but the levels were wrong. Corrected values: 116.6 → 154.4
   → 194.0 → 242.5. If you're citing a gap *level* in future tooltip copy,
   recompute it as `(demandIndex - 100) - supplyIndex` — both zero-based —
   don't mix a raw index with an already-baselined one.

## 8. Application code changes this session

- **`app/api/sheets/route.ts`**: new `computeTfPriceIndexByQuarter()` —
  compounds `nand_price_qoq_pct` chronologically into an index (Q2 2024 =
  100), same baseline convention as supply/demand, computed at render time
  like the other indices (not stored). Exposed as `tfPriceIndexByQuarter`.
- **`app/page.tsx`**:
  - New toggleable "NAND Price Index" line, gap-view only, sharing the main
    `y` axis (normalized to `idx-100`) with supply/demand so all three
    lines are directly shape-comparable — this was deliberate per the
    user's framing that absolute scale doesn't matter here, only shape.
    Revealed a real analytical finding: price has been rising faster than
    supply's index but still sits well below demand's — it's lagging the
    gap, not leading it.
  - **Bug fix**: TrendForce dot forecast/actual styling was hardcoded to
    `quarter === 'Q2 2026'` — a leftover from before this session, when Q2
    2026 was still the forecast quarter. Now derives from the same
    `isForecastQ` flag (added to each chart-data row) that every other
    series already uses. Verified live: was backwards before the fix (real
    Q2 2026 print rendered hollow, Q3 2026 forecast rendered solid).
  - **Bug fix**: Gap Bar's calibration range included forecast quarters,
    so each new larger forecast rescaled and diluted prior actual
    readings. Now filters `allGaps` to `!forecastMeta[q]` (actuals only)
    and adds a fixed `HEADROOM_FACTOR = 0.3` above the actual max so
    forecast quarters still visually separate from each other instead of
    all clamping to the same edge. Position clamped to [2, 98].

Both bugs share a root cause worth remembering: **anything that reads
`forecastMeta` or iterates "all quarters" needs to explicitly decide
whether forecast quarters should be allowed to influence the calculation,
not just inherit whatever the surrounding code already did.** Check this
explicitly on any future series/component that touches the rolling window.

## 9. Supply-side capacity research — full detail (condensed into tooltip fragments, preserved here)

This came from a direct question this session ("what are the supply folks
saying about bringing new capacity online in the next 2 quarters or
beyond") and only survives in the tooltips as a couple of compressed
fragments ("zero new fab capacity in sight," "Yongin cleanroom, early
2027"). Full detail, so November doesn't have to re-derive it — just check
whether anything below has changed:

**Micron** — no new-fab commentary at all this call. Near-term additions
are node transitions on existing lines (1-gamma DRAM, G9 NAND, HBM4 12-High
ramping 2x faster than HBM3E), not new fabs. On timing, MU's own words:
*"We expect tight conditions to persist beyond calendar 2027."*

**SanDisk** — same pattern. BiCS8 already ramped to majority production,
QLC Stargate already shipping, BiCS10 "in development for a long time"
with no mass-production date given. Bit growth objective is modest
(mid-to-high teens %/year). On timing: *"We expect bits to remain on
allocation beyond calendar year 2027."*

**Samsung** — gave the most explicit, quantified answer of any vendor.
CFO Soon-Chul Park: *"considering the lead time from new fab construction
to actual wafer production, which exceeds three years, this means that any
meaningful increase in supply capacity will take considerable time. We
believe it will be unlikely to see any significant increase in incremental
supply through 2028."* Foundry-side: Taylor Fab 1 begins operations in
2026, but **Taylor Fab 2 doesn't start construction until end of 2026,
targeting mass production only by 2030.**

**SK Hynix** — the one vendor with a concrete near-ish date: **Yongin
Cluster Phase 1 clean room opens "early 2027"** — still outside any
2-quarter window, and that's just the clean room opening, not a production
ramp. M15X's mass-production schedule is being "pulled forward" (positive,
no specific new date given). Two brand-new projects (P&T7 packaging, M17
NAND fab) were just announced with zero production timelines. Their own
framing: *"it appears difficult for the supply-demand balance to improve
meaningfully in the near term... due to the increasing complexity of
advanced processes... as well as lead times required for constructing new
production facilities."*

**Synthesis:** every dollar of near-term vendor capex is either (a) node/
technology transitions on existing lines — real bit growth, but not new
fab capacity — or (b) construction spend on facilities that won't produce
a wafer for years. The earliest actual new-facility milestone across all
four vendors is SK Hynix's Yongin Phase 1 clean room, early 2027 — an
opening, not a ramp. This isn't inference — four separate companies
independently told their own investors versions of the same thing: supply
stays structurally tight through 2027 (MU, SNDK) to 2028 (Samsung).

**For the November session:** re-ask this question against the fresh Q3
2026 transcripts and diff the answer against the summary above. A vendor
naming a *new* concrete date, or an existing date moving earlier, is
itself one of the leading-indicator triggers in §10.

## 10. Leading indicators to check every cycle (methodology row, not just this doc)

Full detail lives in the `methodology` table, `field = 'convergence_watchlist'`
— written 2026-08-09 in direct response to this exact "don't want to be
inefficient in November" concern, so check the DB copy is the source of
truth if this doc and the table ever drift. Five things to check against
the fresh Q3 2026 data, not just mechanically refresh:

1. **Any hyperscaler dropping off `mgmt_tone_score = 5`.** All 8 tickers
   hit the ceiling simultaneously in Q2 2026 for the first time — the
   first one to soften its language is the earliest possible tell.
2. **Hyperscaler capex growth RATE decelerating** while vendor capex stays
   elevated — compare each quarter's demand-index point delta to the
   prior quarter's (see the calculation recipe below). Q2 2026 was +37.8pts
   vs. Q1's +16.0pts — accelerating. Watch for that reversing.
3. **Any capacity construction timeline pulled FORWARD** — a second
   pull-forward (SK Hynix already did one, for M15X, this quarter) or any
   new concrete date from another vendor is a real leading signal.
4. **TrendForce QoQ% deceleration trend continuing or reversing** — watch
   the direction across quarters, not any single print.
5. **Genuine industry-wide inventory REBUILD**, distinct from SanDisk's
   current contract-driven build (which is bullish, not bearish). This is
   literally the pattern the DB's own narratives already describe for the
   *last* cycle bottom (Q4 2024/Q1 2025 "post-boom inventory flush").

### Gap-delta calculation recipe (the units bug from §7, made reusable)

Both supply and demand indices must be **zero-based** before subtracting —
`supplyIndexByQuarter` already is (backend-computed as `value - baseline`),
but `demandIndexByQuarter` is raw/100-based and needs `- 100` applied first.
The bug this session came from subtracting a zero-based supply value from a
raw demand value, which is off by a constant +100 — the levels were wrong,
but quarter-over-quarter deltas were accidentally still correct since the
offset cancels in subtraction. Formula: `gap = (demandIndex - 100) -
supplyIndex`. Verified Q2 2026 = 154.4 using this formula; the earlier
216.6/254.4/294.0/342.5 series (still visible in git history) was wrong.
